# 预算口径

现成插件按 token 限额，账单按金额结算。这份文档把两者对上，并说明误差从哪来。

## 单价

`deepseek-flash`，元 / 百万 token：

| | 缓存命中输入 | 未命中输入 | 输出 |
|---|---|---|---|
| 空闲时段 | 0.02 | 1.00 | 4.00 |
| 高峰时段 | 0.04 | 2.00 | 8.00 |

高峰 = 北京时间周一至周五 9:00-12:00、14:00-18:00（法定节假日除外）；其余时段、含周末，全部算空闲，单价减半。

`deepseek-v4-pro` 约为 flash 的 3-7 倍，小群没必要用。

## 为什么不能按 token 数设预算

同一份 100 万 token，全部命中是 0.02 元，全部未命中是 1 元，全是输出是 4 元——差 200 倍。所以：

- token 数只能当**明细**，
- 预算真正该卡的是**折算金额**。

现成插件（`token_controller`）只认 token 数，所以要靠下面的换算把它校准到钱，并且知道它什么时候会失准。

## 换算

取一个典型调用：3000 输入 + 250 输出，输入中 70% 命中缓存。

```
单次成本 = (3000×0.7×0.02 + 3000×0.3×1.00 + 250×4.00) / 1e6 = 0.001942 元
```

于是：

| 调用结构 | 元 / 百万混算 token | 1 元 ≈ |
|---|---|---|
| 命中 70%，空闲 | 0.60 | 167 万 token |
| 命中 95%，空闲 | 0.37 | 269 万 token |
| 全未命中，空闲 | 1.23 | 81 万 token |
| 命中 70%，高峰 | 1.20 | 84 万 token |

同一份 token 限额，落在不同结构上，金额能差 3 倍多。这就是纯 token 限额的真实误差。

## 怎么设限额

`daily_token_limit` 折算成日花费（元/天）：

| 日限额 | 典型 | 高命中 | 全未命中 | 高峰 |
|---|---|---|---|---|
| 0.1M | 0.06 | 0.04 | 0.12 | 0.12 |
| 0.5M | 0.30 | 0.19 | 0.62 | 0.60 |
| 1M | 0.60 | 0.37 | 1.23 | 1.20 |
| 2M | 1.20 | 0.74 | 2.46 | 2.39 |
| 5M | 2.99 | 1.86 | 6.15 | 5.98 |

对一个 <50 人、每天几百条消息的小群，建议起点：

- `daily_token_limit = 2,000,000`　折算约 0.7–2.5 元/天，够用且有冗余
- `user_daily_token_limit = 300,000`　约 0.1–0.4 元，防单人刷
- `refresh_time = 00:00`　与计价日对齐

跑一周后看真实账单，再按「实际 / 折算」的比例回调；如果实际比折算高得多，先查是不是撞了高峰时段。

## 用两级策略近似五档

按费用分档降级是最理想的（省流 → 极简 → 只回 @ → 静默），现成插件只有两级，可以这样近似：

| 想要的效果 | 用插件怎么配 |
|---|---|
| 到 60% 开始省流 | 群策略开「最大上下文窗口 0.5%」+ 关联网能力 |
| 到 80% 只回 @ | 群策略开「仅通过 @bot 触发」 |
| 到 100% 换便宜模型 | `over_limit_policy.action = fallback_provider` |
| 到 120% 静默 | `fallback_token_limit` 设小，用完即停 |

顺序上先砍「唤醒词触发」再做「换模型」，因为前者省的是次数，后者换来的便宜模型仍会消耗。

## 对账

三样东西凑齐才能下结论：

1. `/stats` 的四路拆分（输入缓存 / 输入其他 / 输出 / 总量）
2. 平台账单的当日金额
3. 服务器上有没有别的消耗（检索接口按次计费 5 元/千次，不体现在 token 统计里）

误差 >5% 的排查顺序：高峰时段 → 检索调用次数 → 插件之外来源（其他插件、WebUI 里试聊）→ 是否有中转层改写了 usage。
