# QQ 群 DeepSeek 机器人 技术方案

自托管项目，一个人的小圈子群。本文是这次工作的唯一事实来源，后续实现与派卡都引用这里，不再复述。

## 范围

做一个挂在 QQ 群里的机器人，读全群消息、能被 @ 到位、能主动插一句，用 DeepSeek 回答问题，且 token 支出可控在每月个位数。

不做：多群多租户、Web 管理后台、语音合成回复、图片生成、任何能操作宿主机的工具。

## 已拍板

1. **接入形态**：QQ 群 + 非官方挂号（NapCat／OneBot 11），读全群消息。理由：需要它读全群、不只是 @ 触发；官方 QQ Bot API v2 只收群 @ 消息。
2. **号源与位置**：新注册小号，跑在云服务器。理由：要求 Mac 关机仍在线。
3. **插话阀门**：@ 或点名必回；群里有明确问句且 15 分钟内无人应答时接一句；其余潜水。硬限流：每群每小时 ≤2 次主动、每天 ≤15 次、同一话题冷却 10 分钟。
4. **合规**：纯私人娱乐用途，不接内部系统，不做脱敏层。
5. **能力集**：长期记忆（人名／梗／偏好）、联网检索、发图与表情包、语音转文字。
6. **部署载体**：国内云厂商轻量套餐 2核2G（常见 ¥38–68/年）。不用函数计算。
7. **模型**：默认 `deepseek-flash` 且显式关闭思考模式（`thinking: {type: disabled}`）；`deepseek-v4-pro` 只由白名单指令触发；批量任务排到空闲时段。
8. **每日配额**：按折算金额卡、不按 token 数卡。全局 1 元/天、25 元/月；每人 0.15 元/天 + 20 次调用；单次 `max_tokens=300`、输入 ≤6000 token；五档熔断与对账细则见「每日配额」。
9. **不做预验证**：不等 48 小时验证可行性，环境卡把号挂上即视为上线；2 小时内看是否被踢，被踢则换号重来，不阻塞其余开发。

### 决策证据

- 官方 qqbot 通道只支持 C2C 与群 @ 消息，`group_policy` 白名单管的是哪个群允许用，不是能不能读全群。来源：Hermes 文档 `zh-Hans/user-guide/messaging/qqbot`。
- Lagrange.OneBot 已归档，OneBot 11 实现停止维护；LLOneBot（现 LLBot）依赖 LiteLoaderQQNT 注入且需 GUI，新版 QQNT 会主动检测并下线。两者排除，剩 NapCat。
- NapCat 支持 macOS QQ 7.0.2-53644 无登录启动，Linux 走 Docker 镜像。来源：NapCatQQ release 4.18.36／4.18.37。
- 函数计算三项硬阻断：实例冻结时所有长连接被断开（阿里云开发者社区 512048 官方答复）、FC 无状态且 WebSocket TTL 到期强断 1006、出口 IP 不固定不利 QQ 风控；且常驻实例按月预付，高于轻量服务器。

## 架构

```
QQ 小号
  │  NapCat（Docker，无 GUI）
  │  OneBot 11 反向 WebSocket
  ▼
bot 服务（Python asyncio，单进程）
  ├─ 归档层     全部群消息落 sqlite，FTS5 全文索引
  ├─ 判定层     每 20 条打包一次「哪些值得回」，产出候选
  ├─ 取材层     候选点前后 8 条 + FTS5 检索 top3 历史 + 群滚动摘要
  ├─ 生成层     DeepSeek chat/completions（flash，思考关闭）
  ├─ 发送层     OneBot 11 send_group_msg
  └─ 记账层     每次调用的 hit/miss/output token 与费用落 sqlite
```

发送层做一层抽象（`Sender` 接口），以后若小号被封要切官方机器人，只换实现不改上层。

## 数据流

1. NapCat 收到群消息 → 反向 WS 推给 bot。
2. bot 落库（不调模型），维护每群的环形窗口。
3. 触发判定：
   - 命中 @ 或点名 → 立即进候选。
   - 否则每累计 20 条或每 3 分钟，做一次批量判定，问模型「这批消息里有需要你回答的问题吗，回答第几条」，产出候选。
4. 候选经限流与冷却过滤后，进生成。
5. 生成时只带：系统提示（固定前缀）＋ 群滚动摘要 ≤300 字 ＋ 前后 8 条 ＋ FTS5 top3。
6. 回复发出，记账。
7. 每天 04:00（空闲时段）把当天消息压成滚动摘要，替换旧摘要。

## token 控制

六道闸，从便宜到贵依次拦：

1. **触发闸**　全量消息只落库不调模型；调用次数由「该不该说话」这个批量判定过滤，不由消息条数决定。
2. **上下文闸**　前后 8 条；单条消息截断 200 字；历史只取 FTS5 top3；摘要 ≤300 字。禁止带全群历史。
3. **模型闸**　`deepseek-flash` + `extra_body={"thinking": {"type": "disabled"}}`。思考模式默认开启且 effort=high，不显式关闭会让输出 token 翻几倍。
4. **缓存闸**　系统提示 + 人设 + 群规固定成不变的约 300 token 前缀，动态内容（时间、昵称、消息）全部放在后面。前缀里塞时间戳等于自废缓存（命中价差 50 倍）。
5. **预算闸**　按折算费用卡，不按 token 数卡（三者单价差最高 200 倍，按 token 数卡会把便宜的命中调用先拦掉、放过贵的）。四级配额与五档熔断见「每日配额」。
6. **观测闸**　每日 21:00 汇总（调用次数、命中率、费用、按人分布）推给主号；单日费用超 3 元立即告警。

## 每日配额

### 为什么按钱卡不按 token 卡

同样 100 万 token，缓存命中 0.02 元、未命中 1 元、输出 4 元，差 200 倍。按 token 数设上限，会把大量命中、其实很便宜的调用先拦掉，反而放过少数未命中贵的调用——方向是反的。所以：token 只记明细账，预算判定用折算费用。

记两本账，同一条记录里：token 明细（hit / miss / out，取 API 返回的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、`completion_tokens`，不自己估）+ 折微元费用（1 微元 = 0.000001 元）。

计价时段按北京时间：周一至周五 9:00-12:00、14:00-18:00 为高峰（0.04 / 2 / 8 元每百万），其余含周末与法定节假日为空闲（0.02 / 1 / 4）。同一笔调用落在哪个时段，按调用发起时刻算。

### 四级配额

| 层级 | 默认值 | 折算 | 作用 |
|---|---|---|---|
| 全局每日 | 1.00 元 | 空闲价 ≈ 515 次回话，混算 ≈167 万 token | 主闸 |
| 全局每月 | 25 元 | 低于日均 ×30，留单日突发余地 | 防月末爆表 |
| 每人每日 | 0.15 元 + 20 次 | ≈77 次回话 | 防单人刷 |
| 单次调用 | max_tokens 300；输入 hit+miss ≤6000 token | 单次 ≤0.0031 元 | 防单次爆表 |

典型一次回话（3000 输入、70% 命中、250 输出）空闲价 0.001942 元、高峰价 0.003884 元。配额全部写在 `budget.yaml`，改数字不改代码。

### 五档熔断

| 当日已用 | 行为 |
|---|---|
| <60% | 正常 |
| 60–80% | 禁联网检索（单次最贵项，5 元/千次）；上下文 8 条 → 6 条 |
| 80–100% | 上下文 → 4 条；摘要 300 → 150 字；只回 @ 与点名；回复 ≤80 字 |
| 100–120% | 只回 @；回复 ≤40 字；禁 pro；禁发图 |
| >120% | 静默；被 @ 也只回一句固定话术 |

阈值对应金额：0.60 / 0.80 / 1.00 / 1.20 元，空闲价约 309 / 412 / 515 / 618 次回话。

留 20% 缓冲不是宽松，是因为卡在 100% 会让最后阶段天天被拦——单次调用可能刚好越线，而越线后连一句"额度用完了"都发不出去。

### 计数与恢复

- 内存计数器，每 5 秒或每 10 次调用 flush 一次到 `daily_usage(date, scope, scope_id, calls, hit, miss, out, cost_micro)`。
- 进程启动时先从 sqlite 载入当日已用，**重启不能绕过预算**。
- 自然日 00:00 按北京时间重置，与 DeepSeek 计价日对齐。
- 只信 API 返回的 usage；请求失败但可能已计费的，按"未知用量"记一条待对账项，不静默丢弃。

### 对账与兜底

- 每日 04:05（空闲时段）对账：本地当日 cost_micro 汇总 vs 平台账单，误差 >5% 报警。
- bot 用独立 API Key，模型白名单只给 `deepseek-flash` 与 `deepseek-v4-pro`，防止误配贵模型。
- 单日费用 >3 元立即告警（异常流量信号，比月底才发现好）。
- 余额 <10 元告警，避免静默欠费停机。

## 成本

按 300 条/天、20 次回话/天、70% 缓存命中、flash 空闲价估算：

| 项 | 元/天 |
|---|---|
| 批量判定（15 批 × 800 in / 50 out） | 0.0032 |
| 回话（20 次 × 3K 上下文 / 250 out） | 0.0388 |
| 滚动摘要（1 次 × 5K / 500 out） | 0.0021 |
| 联网检索（5 次 × 5 元/千次） | 0.0250 |
| 合计 | 0.069 |

- 月 token ≈ 2.1 元（全撞高峰 4.2 元）
- 服务器 38–68 元/年 ≈ 3.2–5.7 元/月
- **总支出 ≈ 7.7 元/月，约 93 元/年**

对照：若每条群消息都单独判定，同样规模会到 40 元/月以上——批量判定是这套方案省钱的关键。

## 部署

- 2核2G / 40G ESSD，地域选离群友近的。
- `docker compose` 两个服务：`napcat`（固定 tag，禁 latest）+ `bot`（自建镜像）。
- 两者都 `restart: unless-stopped`；bot 加 5 分钟心跳，NapCat 掉线由 bot 侧检测后重启容器。
- sqlite 与 NapCat 登录态挂宿主目录，重建容器不丢。
- 公网只开 bot 内部端口（127.0.0.1 绑定），不对外暴露 NapCat 的 WebUI 与 OneBot 端口。

## 接口契约

- OneBot 11：反向 WebSocket，监听 `message/group` 事件；发送用 `send_group_msg`，字段 `group_id` + `message`。
- DeepSeek 对话：`POST https://api.deepseek.com/chat/completions`，model=`deepseek-flash`，`max_tokens=300`，`temperature=0.8`，`extra_body={"thinking":{"type":"disabled"}}`。
- DeepSeek 检索：`POST https://api.deepseek.com/v1/tools/search`，5 元/千次成功请求。
- 记账表：`calls(id, ts, group_id, kind, model, prompt_hit, prompt_miss, output, cost, latency_ms)`。

## 验收

1. 群里 @ 它，3 秒内有回复。
2. 模拟「有人提问、15 分钟无人应答」，它接一句；同一话题 10 分钟内不重复接。
3. 连续灌 100 条闲聊，触发 0 次模型调用（触发闸有效）。
4. 记账金额与 DeepSeek 账单对账，误差 <5%。
5. `docker kill napcat` 后 2 分钟内自动恢复。
6. 首月账单 ≤10 元。
7. 断网恢复后不重复回复同一条消息（幂等）。
8. 把 `daily_usage` 当日金额改到 0.85 元再重启进程，后续调用被降级（上下文 4 条、只回 @），而不是照常全量调用——同时证明重启没绕过预算。
9. 把金额改到 1.25 元，只有 @ 得到固定话术，主动插话为 0。
10. 上线 2 小时内确认未被踢下线；若发生，换号重来，保留当次日志用于判断是否为 IP 段问题（而不是 NapCat 配置问题）。

## 风险与降级

- **小号被风控**（最高风险，且已决定不预先验证）：机房 IP 登录，可能几小时内被踢、几天内要重新扫码甚至冻结。这是同类项目的共性，不是本方案独有。
  换号重来的实际代价：重新扫码登录、群成员看到的号变了（要重新介绍一次）、按 QQ 号绑定的偏好记忆需重置，人工约 10 分钟；聊天归档不受影响。预案：预留一个备号；发送层抽象好，必要时切官方机器人方案（牺牲读全群）。
- **NapCat 版本漂移**：QQ 客户端更新后 NapCat 常滞后，镜像 tag 固定、不自动升级。
- **主动插话翻车**：按拍板值上限很低（每小时 2 次），若群友仍嫌吵，直接关到「只回 @」。
- **数据**：sqlite 里是全群聊天记录，落盘权限 600，不做对外接口。

## 未验证

以下几条实现前必须实测，不能当已知：

1. ~~小号在机房 IP 上能否稳定登录并长期在线~~——**已决策：不预先验证**，直接把号挂上去，出问题换号重来。这条从「待验证」降级为「已知且接受的风险」，代价见「风险与降级」第一条。
2. NapCat Linux 无 GUI 的启动方式与镜像选择（release 提到的是 macOS 无登录；Linux 需实测 Docker 镜像与首次扫码流程）。
3. 反向 WebSocket 在容器网络下的连通性（NapCat 主动连 bot，需确认 compose 网络与服务名解析）。
4. 低价轻量套餐能否抢到，抢不到按常规价。
5. `v1/tools/search` 返回结构与配额（文档列了端点与价格，请求体细节未逐字核对）。
6. DeepSeek 控制台是否支持 API Key 级别的每日调用量／金额上限（第三方文章提到「配额管理」，官方文档未确认）。若不支持，预算完全靠本地闸，平台侧只剩余额一条线。
7. QQ 群对个人号机器人的容忍度——无官方策略可查，只能靠低频与不刷屏换取生存期。
