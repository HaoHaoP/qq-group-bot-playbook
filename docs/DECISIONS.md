# 选型记录

四次岔路，每次都在动手前先查「现成方案能不能做」，结论与证据留在这里，避免下次重新走一遍。

## 一、协议端：非官方挂号，不是官方机器人

官方 QQ Bot API v2 只收群 @ 消息，读不到群里的其它对话。需求是「读全群、判断该不该接话」，所以只能用个人号挂号。

三个协议端的现状：

| 方案 | 状态 | 结论 |
|---|---|---|
| NapCat | macOS/Linux 均可无 GUI 运行，2026-10 仍在更新 | 选它 |
| Lagrange.OneBot | 已归档，OneBot 11 实现停止维护 | 排除 |
| LLOneBot（现 LLBot） | 依赖 LiteLoaderQQNT 注入，需 GUI，新版 QQNT 会检测下线 | 排除 |

## 二、载体：轻量服务器，不是函数计算

函数计算跑不了这件事，三条硬阻断：

1. **实例冻结会断开所有长连接**（阿里云开发者社区官方答复），而挂号进程本质就是一条常驻 WebSocket。
2. **出口 IP 不固定**，QQ 号在漂移的机房 IP 上登录是风控靶心。
3. **常驻成本**：FC 要一直在线只有买常驻实例，按月预付，高于 2核2G 轻量（¥38–68/年档）。

FC 唯一成立的位置是另一条路线——官方机器人 webhook，事件驱动、零常驻。但那等于放弃读全群。

## 三、框架：AstrBot，不自研

自研一整套（WS 服务 + 会话 + 重连 + 发送 + 存储）约 1500 行，而 AstrBot 把这些全给了，还带管理面板、插件热载、多平台适配。

关键事实：AstrBot 的插件能收到全部群消息事件（`filter.EventMessageType.ALL`），所以「读全群」不需要自研框架。

不选自研的另一个理由：插件层不绑定协议端，NapCat 将来挂了，换适配器即可，插件不用改。

## 四、插件：用现成，不自研

这一层查得最久，因为「预算管理」看起来必然要自己写。查到的情况：

| 现成物 | 覆盖 | 缺口 |
|---|---|---|
| AstrBot 自带 `/stats` | 四路 token 拆分、会话与总览统计 | 只统计，不拦截 |
| `astrbot_plugin_token_controller` | 群级/用户级日配额、到量换模型或停、仅@触发、上下文压缩、DeepSeek 稳定前缀、统计看板 | 按 token 不按金额；两级而非五档 |
| `astrbot_plugin_private_companion` | 内置 token 预算 + DeepSeek 峰时替换 | 只管自己内部任务，README 明写「外部插件统计不并入本插件限额」 |
| `astrbot_plugin_composting_bucket` | 专压 DeepSeek 费用 | 已并入 AstrBot，可从清单移除 |
| `smart_wake` / `wake_pro` / `group_chat_plus` | 主动插话与唤醒判定 | 判断的是「要不要参与聊天」，不是「这条问题有没有人答」 |

官方插件索引里搜「预算 / 费用 / 金额 / budget」命中为 0。

结论：真正没人做的只有「按金额口径卡预算」和「五档熔断」两处，而这两处对一个几百条消息/天的小群带来的差异，远小于写 200 行插件并长期跟 AstrBot 版本漂移的成本。所以**不写插件**，把换算与调参写进 `BUDGET.md`。

如果哪天群变大、有人刷、或大量调用落在高峰时段，这两处缺口才会值钱；那时的正确做法是提 PR 给 `token_controller`，而不是另起一个插件。

## 五、验证：不做预验证

用户决定：不预先花 48 小时验证小号能不能在机房 IP 长活，直接上线，出事换号。

记录的代价：重新扫码、群友看到的号变了、按号绑定的偏好记忆重置，人工约 10 分钟。聊天归档不受影响（本方案不做归档，只记用量）。

## 走过的弯路

- 一开始的方案是自研全套（NapCat → 自写 Python 服务 → sqlite → DeepSeek），并写好了成本折算与五档预算的核心模块。发现框架层全是重复劳动后废弃。
- 第二版方案是 AstrBot + 自写插件（金额预算 + 批量插话判定 + 全文取材，约 400 行）。查到插话已有现成插件、限额已有 `token_controller` 之后再次收缩。
- 两版被放弃的代码没有进这个仓的历史；判断与数字保留在 `BUDGET.md` 与本文里。
